timetap

A personal time-logging web app. Google Apps Script, four files, no dependencies.

Automate capture. Never automate judgment.

Logging costs one tap. The app never interprets, scores, advises, summarises, reminds or nudges. Every conclusion is drawn by the human, later, elsewhere.

You maintain a PLAN calendar by hand — intent, written Sunday. The app writes an ACTUAL calendar — record, written continuously — plus a SITTING calendar as a posture overlay. Comparing them is a weekly manual ritual the app does not participate in beyond emitting raw numbers.

Files

  • appsscript.jsonManifest. Three OAuth scopes. Set your timezone here.
  • Code.gsServer. CONFIG block, calendar reads and writes, the nightly rollup.
  • Index.htmlClient. All HTML, CSS and JS inlined. No CDN, no build step.
  • SETUP.mdDeployment steps and the required Google Calendar settings. raw

The open-block mechanism

The calendar is the source of truth, not localStorage. Tapping a category immediately creates an event with start = now, end = now + 1 minute, and #open in the description. The next tap patches the end to that instant, applies the mark, and strips #open.

This survives a dead battery and a reinstall. On load the open block is found by querying the calendar, not by trusting the browser. The UI updates on tap; the write happens in the background, and a failed write is queued in localStorage — ordered and idempotent — then retried on the next interaction and on load.

The grid fills from the bottom row up, so the first entries in CATEGORIES land nearest your thumb. There is no bar above it and no chrome below it: the note and the clock belong to the block that is running, so they live inside the box that is running, and the ring around it breathes. The + box names a new category, up to ten; nothing can be renamed afterwards, because a key change would split every past event away from every future one in the rollup. There is no chrome below the grid: the lit button is the open block, so re-tapping it opens SPLIT, and when a closed block earns a mark the + = - strip takes the posture row's place for six seconds — same slot, same height, so nothing above it moves.

A tap that lands within a minute of the previous one arms the button rather than committing, and waits for a second tap. Taps that close together are far more often a brush than a decision, and the correction rule makes a brush destructive: it silently retitles the block you are actually in. Ignoring the question is the safe outcome — it forgets after four seconds and nothing was ever queued.

The mark

The mark belongs to the block that just closed, captured at the transition — the one moment you both know how it went and are already holding the phone. Never asked for on a block that is starting.

A closed block shows the + = - strip only if its category has no autoMark and it ran at least MIN_MARK_MINUTES. Ignoring the strip costs zero taps: it dismisses itself and = stands. You should see it two to four times a day. If you see it constantly, the design has failed.

Posture

Posture is an overlay, not a seventh category. Categories are a partition — exactly one true at a time. You sit while doing deep work, meetings, meals.

One button below the grid, reading SITTING or NOT SITTING. Only sitting is written down: not sitting is the absence of a SIT block rather than a row of its own, which is why the button needs nothing remembered to know what it says — clear the browser's storage and it still comes back right. Non-sitting time is computed at review as waking span minus sitting, and only sitting carries a duration, because only sitting has a start to count from.

That duration is also the way in to correcting when it started, which is the only moment such a correction means anything.

The only coupling in the entire app: tapping BODY closes an open SIT block and drops the button to not sitting. That is definitional, not inference. No accelerometer, no screen time, no heuristics, ever.

The numbers

There is no week screen. A daily trigger rebuilds two tabs of a Google Sheet straight from the calendars, and you read them where you do your thinking — which was never a phone.

daily is one row per day for ninety days: hours per category, planned hours per category, switches, waking span, sitting hours, sitting percentage, longest unbroken sit, sits over ninety minutes. weekly is the same numbers grouped Monday to Sunday with the planned-versus-actual ratio the weekly ritual compares.

Both tabs are rebuilt from scratch on every run rather than appended to. That makes the job idempotent, lets a calendar you correct on Thursday fix Tuesday's row, and keeps the columns honest when the category list changes. It also makes them generated output: put your own work in another tab and point formulas at these.

Everything is a real number rather than a padded string, so the spreadsheet will sum, pivot and chart it without being asked twice. The app emits the grid and stops. No charts, no highlighting of problem rows, no commentary, no comparison to last week — the spreadsheet will do all of that if you ask it to.

Non-goals

  • Notifications, reminders, alerts, nudges, sit-time warnings
  • Any automatic detection: screen time, location, motion, calendar inference
  • Streaks, scores, badges, gamification, encouragement
  • AI summaries, insights, recommendations, generated review text
  • Charts, graphs, sparklines, progress bars
  • Accounts, auth, databases, external services, analytics
  • A settings screen — configuration is the CONFIG block in Code.gs
  • Writing to the PLAN calendar in any way
